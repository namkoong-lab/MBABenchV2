Rubric: "Column widths must be sufficient to display all values without truncation or '###'."
Good: "All values display fully; no truncation or '###'." Bad: "Some columns truncate values or show
'###'."

## Rule as implemented

A visible **numeric or date cell** (constant or formula result; array / dynamic-array spill members
included) FAILS when the text Excel displays for it is wider than its column's text area under
**every** platform model by more than `SURE_TOL_PX` = 2 px (96-dpi pixels). This is a "sure
overflow": Excel shows `####` whatever the viewer's platform (report.md approach C). A cell that
overflows under some models only is a **band** case: counted and exemplified in stats
(`band_cells`, `band_examples`), never a mistake.

**Cut-off text** (Patrick 2026-10-04, option 3): visible text of **200 or more characters** that cannot
be fully seen fails - unwrapped text whose overflow is blocked (a), wrapped text needing more lines than
its custom-height row shows (b). Shorter cut-off text (a row label clipped by the next cell, ...) passes
and is counted in stats; text running into empty neighbours and staying visible passes. See "Cut-off
text".

Scope and exemptions:
* Every worksheet, dialog sheet and macro sheet of the delivered workbook. **Hidden sheets are
  graded** (whole-workbook rule, as Reasonable row heights (73) and Zeros as dashes (66) do); the
  mistake text says "(hidden sheet)".
* **Cells in hidden rows or columns are skipped** (`hidden="1"`, `ht=0`, zero width, or no `ht` on
  a `zeroHeight` sheet): nothing is displayed there, and No hidden rows/columns (93) owns them.
  Counted in `hidden_row_cells` / `hidden_col_cells`. **Exception (second review 69-F4,
  `HIDDEN_ANCHOR_SPAN = True`):** the anchor of a merge whose own row or column is hidden while the
  span still has a visible column and a visible row: Excel draws the merged value across the
  visible part, so the anchor is measured against the span's visible columns in a second pass
  (`hidden_anchor_cells`). E.g. A hidden, B 26 px, merge A1:B1, A1 = `123456789` (format `0`) →
  fail. A one-row merge whose row is hidden, or a span whose columns are all hidden, shows nothing.
* **Shrink-to-fit** cells never show `####` (exempt; `shrink_to_fit` count).
* **Negative or out-of-range dates** show `#####` at any width; not a width defect
  (`NEGATIVE_DATE_FAILS = False`; `negative_dates` count).
* **Fill, centre-across-selection and rotated numbers** are skipped: how Excel clips them is
  unverified (`skipped_alignment` count).
* Booleans and errors are not values this check measures (errors are No formula errors (22)'s
  domain). A number whose format prints nothing (`;;;`) displays nothing (`blank_display`).
  A formula result counts as a number, text, boolean or error by its **trusted value**, never by
  the delivered `t` attribute (second review 69-F1, see "Values").
* Covered (non-anchor) cells of a merge are not displayed; the anchor has the summed span.

## The width model

**Platform models** (`MODELS`): `w96r`, `w96f`, `w120r`, `w120f` = Windows 96 dpi and 120 dpi
(Excel for Mac sits on the 120-dpi grid: a 9 px Calibri-11 digit), each with per-glyph **rounded**
advances (GDI) or **fractional** advances. Overflow of a model is converted to 96-dpi pixels
(`× 96 / dpi`) before the 2 px tolerance is applied. `w96r` is the reference model (strict default
column reading; quoted in messages).

**Column unit.** `MDW(model)` = the Normal font's widest digit in whole pixels at the model's dpi:
`round(adv_em(digit) × size × dpi / 72)`. 7 px for Calibri 11, Aptos Narrow 11 and Arial 10 at 96 dpi;
9 px at 120 dpi. The Normal font is the font of the `Normal` cell style (builtinId 0), else
`fonts[0]`. The stored `<col width>` includes padding (ECMA-376 18.3.1.13: Excel's UI shows
`(px − 5) / MDW`; the default UI 8.43 is 64 px; UI 12.0 is stored 12.7109375 = 89 px).

**Column pixels** (ECMA-376 `col/@width`):

    px(w, MDW) = trunc(((256 · w + trunc(128 / MDW)) / 256) · MDW)          e.g. px(8.7109375, 7) = 61
    no <col>:   base = baseColWidth (default 8): ceil((base · MDW + 5) / 8) · 8     → 64 px (Calibri 11, 96 dpi), 80 px at 120 dpi
                with sheetFormatPr/@defaultColWidth w: strict = px(w, MDW); lenient = max(strict, trunc(w · MDW + 5), base px)
                (the lenient reading applies in every model but w96r: Excel's reading of a LibreOffice-written
                8.5390625 - 60 px strict, 64 lenient - is unverified)
    hidden column, or width <= 0:  not displayed
    text area = px − CELL_MARGIN_PX (5)       merged anchor: sum of the span's columns − 5

**Which `<col>` entry applies** is the core reader's one rule (`SheetHead.col_info` / `col_run`,
docs/reader.md §7): where entries overlap (invalid; GPT-6 tooling in 187 corpus files) **the later
entry wins**, as in Reasonable column widths (70) and Reasonable row heights (73). Until 2026-10-04
`col_info` returned the sheet default for every column an earlier range covers after a later entry
that starts inside it (`C:XFD 18` + `D:D 3`: F onwards measured at 8.43); the room walk
(`_SheetGeo.room`) followed the same reading. Corpus effect: CHANGELOG_core.md (2026-10-04).

**Text width.** `need(model) = Σ glyph advance + pads + indent`, in model pixels:
* Glyph advances in 1/1000 em per face and weight (`GLYPHS`, 116 characters: digits, punctuation,
  currency, letters for month / day names and `E`, dashes, nbsp), read once from the real font files
  with fontTools by `scratch/colwidths/glyph_table.py` and embedded (stdlib only at grading time).
  Faces: Calibri, Calibri Light, Arial, Arial Narrow, Aptos Narrow, Aptos, Times New Roman, Verdana,
  Tahoma, Georgia, Courier New, Consolas, Cambria, Century Gothic, Candara, Corbel, DejaVu Sans, bold
  cuts included; aliases Helvetica / Liberation Sans / Arimo / Arial Unicode MS / Roboto → Arial
  (Roboto digits 0.562 em vs Arial 0.556), Carlito → Calibri, Aptos Display → Aptos, Liberation Serif
  / Tinos → Times New Roman, Liberation Mono / Cousine → Courier New.
* `ppem = size × dpi / 72`. Rounded model: `Σ round(adv × ppem / 1000)` per glyph (plain rounding; the
  fonts' `hdmx` device tables agree with it for Arial regular at every size 10-24 ppem, and Calibri /
  Aptos / Aptos Narrow carry no hdmx; Times New Roman and Georgia would differ by ±1 px per glyph).
  Fractional model: `Σ adv × ppem / 1000`.
* The cell's **own face, size and weight** (judge v12 rule). Unknown faces (Segoe UI, ...) are measured
  as **Calibri**, the narrowest common face, so they miss rather than flag falsely; listed in
  `unknown_faces`. A glyph a face lacks counts as a digit.
* Padding tokens `_x` of the format section used are measured as the glyph x instead of the space the
  renderer printed (accounting `_)` = a parenthesis). `?` blanks stay a space (Excel: a digit width;
  lenient). `*x` fill adds nothing.
* Alignment indent (left / right / distributed; both sides for distributed) takes
  `INDENT_SPACES_PER_LEVEL` (3) Normal-font spaces per level off the text area (whole px at the model's
  dpi), as in Reasonable row heights (73).

**Displayed text.** `detchecks.core.numfmt.render(value, code, value_type, date1904)` with the cell's
resolved format (`N.resolve_format(numFmtId, styles.num_fmts)`: a workbook `<numFmt>` wins, then the
en-US built-in table; an undefined id raises `GradingError`). `t="d"` ISO dates are rendered as dates.
A conditional-format number format replaces the cell's where its rule fires (below).

**General format** (`GENERAL_SHORTENS = True`): Excel never shows `####` for a General number while a
shorter rendering exists - it rounds decimals away and falls back to `d E+nn` scientific notation. The
need of a General cell is the narrowest of its full text, its 0-decimal rounding and its 1-digit
scientific form (`general_alternatives`): `123456789` in a default column shows `1E+08`; `0.75` in a
1.5-character column shows `1`. A General cell can therefore fail only in a column narrower than
`-dE+nn` (about 40 px). An ISO-typed date (`t="d"`) under General shows its serial (`46023` for
2026-01-01, as numfmt renders it); the shortenings start from that serial (second review 69-F5:
they used to start from 0, so such a cell could never overflow). Excel itself never writes `t="d"`.

**Decision per cell:**

    over(m) = (need(m) − text_area(m)) × 96 / dpi(m)        for every model m
    sure overflow  ⇔  min_m over(m) > SURE_TOL_PX (2.0)     → mistake
    band           ⇔  over(w96f) > 2 but some model ≤ 2      → stats only
    fit            ⇔  over(w96f) ≤ 2                          (the fractional 96-dpi model is itself one of the
                                                              four, so this pre-screen is exact, not approximate)

**Calibration.** Toy T2 Fail: the check flags exactly the 62 cells of `'Daily Model'!BBB` the
Overview counts ("62 of its 128 numeric cells display ####"), and 5 band cells (e.g. BBB2
`10/30/2033`: +1.0 / +3.7 / −0.8 / +0.3 px). Toy T1 Pass: J is 89 px (12.0 UI characters); the
widest value `22,852.00` needs 57 px (8.11 UI characters by the Overview = 56.8 px). The report's
2100 case: `($11,540,911.76)` needs 97 px against 93 (report: "about 97 px against 93").

## Cut-off text (Patrick 2026-10-04)

Patrick's decision: Sufficient column widths (69) also fails on **cut-off text anywhere in the
workbook**. Text that runs into empty neighbouring cells and stays fully visible is fine; text that
cannot be fully seen fails.

**DECIDED 2026-10-04 (Patrick): option 3, only cut-off text of 200+ characters fails**
(`TEXT_CLIP_MIN_CHARS = 200`, one bar for (a) and (b)). The first version failed cut-off text of any
length; it failed all four Pass toys (their goldens hold cut-off labels of 14-158 characters) and 64
of 71 attempts ("Sanity run of the any-length rule"). Shorter cut-off text passes, as the toys and the
judge guidance ("a text label that runs a few characters past its column is ordinary formatting
practice") treat it, and is **counted in stats, not in the verdict**: `text_cut_off_short`,
`wrapped_cut_off_short`, `text_blockers_short`, `text_cut_off_short_examples` /
`wrapped_cut_off_short_examples` (cell, text start, characters, what cuts it off), per sheet
`text_cut_off_short` / `wrapped_text_cut_off_short`; the summary says how many. Every other rule and
edge-case decision below is unchanged and applies to the long texts.

**How characters are counted** (`shown_chars`): the cell's displayed text - the value after its number
format (a text section's prefix or suffix counts, `;;;` shows nothing) - without leading and trailing
blanks (spaces, tabs, non-breaking spaces, line breaks) and without the typed line breaks inside it
(an unwrapped cell shows them as nothing, a wrapped one as a new line). Every other character counts
once, blanks inside the text included; rich-text runs count by their characters. A text of 200 shown
characters fails when cut off, 199 passes. It replaces the two narrow rules of the
build (`TEXT_NUMBER_CLIP`: a number stored as text cut off; `TEXT_HIDDEN_COL_MAX_PX`: any text in a
≤ 12 px column blocked), which were cases of it: their constants, `_NUMLIKE`, `TEXT_WALK_MAX_COLS`
and the stats `text_number_clips` / `text_hidden_col` / `text_overflow_into_empty` are gone. The
'####' rule for numbers and dates is unchanged.

**What is text.** A visible cell showing a string: a constant (`s` / `inlineStr` / `str`; numbers
stored as text included) or a **trusted** text formula result (a formula's value routed as in 69-F1;
errors and booleans are not text). The display goes through the cell's number format: a format with a
text section can add to the string (`@" (in millions)"`), pad it (`_(@_)`: pads are blanks), or blank
it (`;;;`: nothing shown, `text_blank_format`). An empty string shows nothing (it still stops
overflow). Same scope as the numbers: hidden rows / columns skipped (a text merge anchor in a hidden
row or column is measured on the merge's visible part, 69-F4, `text_hidden_anchor_cells`), hidden
sheets graded.

**Width.** The same machinery as the numbers: the four platform models (`MODELS`), the cell's own face,
size and weight (`GLYPHS`; unknown faces as Calibri, listed in `text_unknown_faces`), per-glyph rounded
or fractional advances, alignment indent (left / right / distributed: 3 Normal spaces a level), column
pixels per model. Characters outside the glyph tables: accented letters as their base letter, East Asian
wide characters 1 em, combining marks 0, a tab as a space, anything else a digit (`resolve_char`, now
shared with Reasonable column widths (70)). Rich text is measured run by run in each run's size and
weight (the reader keeps no run face: the cell's); a run size outside Excel's 1-409 pt range (ChatGPT's
writer stores `1000` for 10 pt) is ignored - the cell's size is used, so it never enlarges the text
(`MAX_FONT_PT`, counted in `text_runs_size_out_of_range`). **Blanks at the ends are invisible**: a leading
blank pushes left-aligned text right, a trailing one pushes right-aligned text left, centred text is
centred including both; only the visible glyphs (first to last non-blank character) must fit.

### (a) Unwrapped text (`TEXT_CLIP = True`)

Cut off when the visible glyphs reach past the space the text may use **under every model by more
than `SURE_TOL_PX`** (2 px at 96 dpi) - the numbers' "sure overflow" logic (Patrick ruled 2026-10-04:
keep it). Under some models only: a band case, counted (`text_band`, `text_band_examples`), never a
mistake.

Space = the text area of its column (`px - 5`) plus the contiguous **empty** cells in the direction it
overflows:

| alignment | overflows | must fit |
|---|---|---|
| general (text), left, unknown | to the right | indent + leading blanks + glyphs ≤ area + room on the right |
| right | to the left | indent + trailing blanks + glyphs ≤ area + room on the left |
| center | both ways | half of (text − area), trailing / leading blanks deducted, on each side ≤ that side's room |
| centerContinuous (centre across selection) | both ways | as center, over the cell plus the contiguous empty cells to its right with the same alignment (their own `<c>` style, or for cells without `<c>` the row's / column's style) |
| fill | never | glyphs ≤ the cell plus the contiguous empty fill-aligned cells to its right |
| justify / distributed, wrapText | - | wrapped: rule (b) |
| shrinkToFit | - | never cut off (`text_shrink`) |
| textRotation ≠ 0 | - | skipped (`text_rotated_skipped`; how Excel clips rotated text is unverified) |

Overflow stops at the first **non-empty** cell: a value (number, date, text - an empty-string constant
included), any formula result (a formula returning `""` too, also an untrusted one), a boolean or an
error (`text_blockers` counts what stops each cut-off text). Also:
* **Merged cells take no overflow** (`MERGES_BLOCK_OVERFLOW = True`): a merged range in the path stops
  the text at its first column, even when empty (Excel's behaviour as I know it; not measured).
* **Hidden columns**: an empty cell in a hidden (or zero-width) column lets the text through but gives
  it no room (0 px); a **filled** cell in a hidden column still stops it (`HIDDEN_CELLS_BLOCK_OVERFLOW =
  True`; Excel checks the cell, not its visibility - believed, not measured; the mistake says "in
  hidden column B").
* **The sheet's edges**: nothing beyond column A or XFD - right-aligned text in A or general text in
  XFD that overflows is cut off ("the left / right edge of the sheet").
* **Text never spills out of a merge**: a merge anchor's space is the merge's visible width (hidden
  columns of the span count 0) and its alignment decides which end is clipped; covered cells are not
  displayed (`text_covered_merged`).
* **Typed line breaks** in an unwrapped cell show as nothing: the text stays on one line.

### (b) Wrapped text (`WRAPPED_TEXT_CLIP = True`)

Wrapped text (`wrapText`, or horizontal / vertical justify / distributed, as Reasonable row heights (73)
wraps them) is cut off when it needs more lines than its row shows - **only in rows with a custom
height** (`<row customHeight="1" ht=...>`). Excel auto-fits every other row on open
(docs/excel_measurements.md item 6), so wrapped text there is never cut off (`wrapped_auto_rows`). A
sheet-level custom default height is not used (rows without their own height count as auto-fitted).

* **Lines** = Reasonable row heights (73)'s greedy word wrap (`c73.wrap_lines`: paragraphs at typed line
  breaks, words at spaces, a word wider than the line broken by characters), fed with this check's
  per-glyph widths in the column's (or merged span's) text area minus the indent, under each model;
  the **fewest** lines count (`lines_by_model` in stats examples). Trailing blanks and line breaks show
  nothing. Rich text is laid out in its narrowest font (smallest run size, regular unless every run is
  bold) - lenient.
* **Line height** = Reasonable row heights (73)'s `LINE_HEIGHT_PER_PT` (1.3) × the font size (rich text: the smallest run size).
* The row shows `height / line height` lines; the text is cut off when more than
  `WRAP_HIDDEN_LINES_TOL` = **half a line** is hidden (a line counts as shown when at least half of it is
  visible). The tolerance absorbs Reasonable row heights (73)'s line height against Excel's (Excel's auto-fitted pitch is 1.25-1.42
  × size, e.g. 12.75 pt for Arial 10, 15 pt for Calibri 11): with it, a row at Excel's own auto-fitted
  height never fails below 13 lines of Arial 12 or 27 lines of Arial 10.
* A merge over several rows: its block height is the sum of its visible rows' custom heights; with any
  auto-fitted row in the block it is not graded (`wrapped_merge_auto_rows`). Excel's AutoFit ignores
  merged cells, so a wrapped merge anchor in an auto-fitted row can be cut off in reality: such anchors
  needing more lines than their rows are counted only (`wrapped_merged_in_auto_rows`, examples) - not
  graded under the ruling "rows without a custom height never cut wrapped text".
* Under some models only: band (`wrapped_band`).

`WRAPPED_TEXT_CLIP = False` keeps every count but adds no mistake; `TEXT_CLIP = False` likewise for
(a); `TEXT_CLIP_MIN_CHARS = 0` grades cut-off text of any length (the first version). Stats
`mistakes_by_rule` = {numbers, unwrapped_text, wrapped_text} counts the mistakes (blocks) of each rule;
`text_cut_off` / `wrapped_cut_off` / `text_blockers` count the graded (200+) cut-offs, the `_short`
keys the others; band counts (`text_band`, `wrapped_band`) cover every length.

Info only (not graded): one line of unwrapped text in a custom-height row lower than half a line
(`text_rows_under_half_line`, examples) - text hidden vertically by a tiny row.

### Values for text

A text formula result needs its trusted value like a number does (69-F1). Untrusted formula results
were already undecided for the numbers; two consequences of the text rule:
* **69-F2 narrowed**: an untrusted result is "not displayed whatever its value" only when its format
  prints nothing for numbers **and** text (`;;;`, `blank_for_any_value`). Under `;;` (no text section) a
  text result shows as typed, so such a cell stays undecided.
* An untrusted result in a fill / centre-across cell (skipped by the number rule) is undecided for the
  text rule.

## Numbers: values, conditional formats

### Values (needs_values)

Constants are read from the file and routed by their stored type (`n` / `d` with a value element →
measured; strings → the text rules; booleans and errors → not measured).

A **formula result** (own formula, `<f/>` marker or array / spill member) is routed by its **trusted
value, never by the delivered `t` attribute** (second review 69-F1). `t` belongs to the cache: agent
tools write `t="str"` placeholders with empty caches (openpyxl 227,532 such cells in the attempts;
ChatGPT's writer 1.4 M `<c t="str"><f>…</f></c>` cells with no `<v>` in GPT-6), LibreOffice writes
`t="e"` `#NAME?` placeholders. Before the fix such a cell was skipped as text / boolean / error
without being read, so a wide number behind it passed even when a value copy held it.
* A **trusted** value (Excel cache, LibreOffice / Excel recalculation copy, unknown-writer cache with
  a value) is read (`formula_values_read`): a number (or a cached ISO date) is measured; text, a
  boolean or an error is not (`formula_nonnumeric`). With a value copy the **copy's** value type
  decides: a `t="str"` placeholder whose copy holds `123456789` is measured and fails; a numeric
  placeholder whose copy holds text is not measured.
* The recalc pipeline vets a LibreOffice copy's `#NAME?` / `#VALUE!` values (gap scan; with Excel
  off, `errors_vetted = True`), so in production those cells are **trusted errors and skipped
  without a loud error**, exactly as ruled 2026-10-04 ("match v12").
* An **untrusted** value (openpyxl / XlsxWriter cache, no cache, a LibreOffice-written `#NAME?` /
  `#VALUE!` cache read without the pipeline or with an unvetted manual copy, cell missing from the
  copy) leaves the cell **undecided whatever its placeholder type** (`t="str"` / `"b"` / `"e"`
  included), with two exceptions where the display cannot depend on the value (second review
  69-F2; `undecided_not_displayed`): a **covered (non-anchor) cell of a merge** is never displayed,
  and a cell whose own format prints nothing for every number (`;;;`, `;;`: all numeric sections
  empty) shows nothing - unless a format-setting conditional rule covers it, which keeps it
  undecided. Shrink-to-fit, hidden and skipped-alignment formula cells are never read either.

Undecided cells:
* if the workbook fails on measured cells anyway, undecided cells are listed in stats
  (`undecided_cells`, `undecided_examples`) and the summary says so; nothing is raised
  (`UNTRUSTED_ONLY_IF_VERDICT_NEEDS = True`, the same option as 73);
* otherwise the first undecided cell raises `GradingError` naming the cell, the writer and whether a
  value copy was given (no fallback).

The same mechanism covers a rendering numfmt marks `certain=False` when it would be a sure overflow
(a covered merged cell is dropped here too), and a conditional-format outcome set that disagrees
(below; a first-pass unverified rendering inside a format-setting rule's range is superseded by the
second pass, which renders every possible outcome).

Because every formula result matters here (unlike 73, where only wrapped formula cells do), an
openpyxl / uncached attempt **without** a value copy errors unless a constant already fails - since
the second review also when its only formula results are `t="str"` placeholders, and a
LibreOffice-written file with `#NAME?` / `#VALUE!` caches graded without the pipeline. Production
supplies the copy for every non-Excel file (ruling 2026-10-03; the recalc pipeline), so these
errors are the sanity run's artefact of missing copies (11 of 71 attempts have one).

### Conditional formats

`_cf_rules` collects, in priority order, the rules whose dxf sets a number format (`dxf.num_fmt_code`,
else `num_fmt_id` resolved) and the `stopIfTrue` rules (data bars, icon sets, colour scales never set
a format). A sheet with such rules is streamed a **second time**: every numeric cell inside their
ranges is rendered under each possible outcome - `c66.fires` says which rules fire on the value
(`cellIs` with literal operands, blanks/errors, text rules, literal expressions and `<self> <op>
<literal>` expressions); unknown rules branch (at most 8 per cell, else `GradingError`). The cell
fails only if **every** outcome is a sure overflow (noted "conditional-format number format …" when the
deciding format is the CF one); it passes if none is; a disagreeing set is undecided (raises unless
the file fails anyway). First-pass candidates inside those ranges are handed to the second pass.
`t="d"` cells under CF: every covering format is possible (the ISO value is not compared). The
second pass routes cells exactly as the first (constants by stored type, formula results by trusted
value, 69-F1) and also measures the hidden merge anchors of 69-F4 (requested cell by cell when the
sheet has no format-setting rule).

## Mistakes

runs stacked), e.g. `'Solution Model'!J7:J15`, with the worst cell of the rectangle as the example:

> 9 numeric cells J7:J15 on sheet 'Solution Model' display '####' in Excel: column J is too narrow for
> the values; e.g. J7 shows '22,852.00' (Arial 10, number format "#,##0.00;\(#,##0.00\)"), about 36 px
> wider than the column's text area at 96 dpi and overflowing under every platform model (96/120 dpi,
> rounded or fractional glyph widths).

Capped at 25 (base contract); `stats.sure_overflows` holds the full count and `per_sheet` the split.
Cut-off text: one mistake per rectangle of cut-off cells per rule (see "Mistakes (text)"); number
mistakes come first on each sheet. Severity "major" (the detchecks default).

## Known limits

* No hdmx / hinting: per-glyph plain rounding. Exact for Arial regular; Times New Roman, Georgia,
  Tahoma bold, Verdana differ by a pixel per glyph at some sizes (rare on numeric cells).
* The platform band is a model, not a measurement: nothing here was checked in real Excel (the
  2.0 px tolerance comes from the report's calibration on an author-fitted column, +0.8 px under the
  most lenient model). The toy T2 count (62 = Excel's 62) is the strongest evidence so far.
* Zoom is 100 %. T2's Overview notes the unfixed golden shows `####` at 100 % but not at its stored
  80 % zoom; the stored zoom is ignored (Question 4).
* Rich-text numbers do not exist. Rich-text labels are measured run by run (size, weight); a run's own
  face is not read (the reader keeps none), the cell's is used.
* Cut-off text, not measured in Excel: centred text clipped at the sheet's left edge, merged ranges
  and filled hidden cells stopping overflow, centre-across overflowing beyond its selection, fill text
  clipped at its selection; rotated text skipped (Question 15). Label widths are not calibrated against
  Excel: T4's Overview gives B19 17.56 characters where the 120-dpi rounded model measures 19.2 (the same
  model reproduces the Overview's 8.11 for a number exactly); if Excel lays labels out narrower (kerning,
  Mac rendering), the 2 px sure tolerance does not cover it for long labels (Question 16; T4 B19 is cut
  off either way).
* Wrapped text: Reasonable row heights (73)'s 1.3 x size line height and greedy wrap (no hyphen breaks); rows auto-fitted by
  Excel are trusted, even for merged cells Excel's AutoFit ignores (counted in
  `wrapped_merged_in_auto_rows`); a sheet-level custom default row height is not used.
* Right-to-left sheets are measured as left-to-right (overflow directions not mirrored; rare).
* `?` placeholders are measured as spaces (lenient by ~3 px each in accounting zero sections).
* Column styles / row styles do not matter: only cells with values are measured.
* Second pass for conditional formats re-reads the whole sheet part (only sheets with format-setting
  rules).
* A sheet whose rules carry a format over very large ranges (whole columns) evaluates every numeric
  cell there; `fires` is cheap, but the outcome branches (`2^unknown`, ≤ 8) are per cell.
* With a LibreOffice copy the engine merges the copy for every formula cell (as 73 / 66 / 94), so
  attempts with huge copies are slow (4091: 375 MB copy; see the sanity timing).
* A value-copy cell typed `t="d"` is read as text (not measured): only the delivered file's own cached
  ISO date counts as a date. Neither Excel nor LibreOffice writes `t="d"`.
* Hidden merge anchors (69-F4) cost a second stream of the sheet, requested only for sheets with such
  a merge and at least one value / formula cell in a hidden row or column.
