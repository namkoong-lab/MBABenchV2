## Rule as implemented

A **populated** cell fails when its content cannot be seen:

* **(a) colour** — its text colour is effectively the same as its **own** background:
  APCA lightness contrast `|Lc(text, background)| < 12` (`CONCEAL_LC`) **and** the two colours
  do not clearly differ in hue (`HUE_EXEMPT`, below); or
* **(b) number format** — its number format prints nothing for its value
  (`numfmt.render(value, format).is_blank`): `;;;`, an empty section (`0;-0;;@` on 0,
  `#,##0;(#,##0);` on 0), `#,###` on 0, a space-only literal section.

Both are checked on every worksheet, dialog and macro sheet (hidden sheets, hidden rows and
columns included; whole delivered workbook, no starting-file diff). One mistake per rectangle
of cells sharing the same reason (`add_cell_mistakes`); a cell concealed both ways (94 T3
`Z412`: white font **and** `;;;`) gives one mistake naming both.

**Populated** = the displayed value is not empty: a number, boolean, error, or text with a
non-space character. Empty cells (no value, no formula) never count, nor does a formula whose
result is `""` or spaces (94 T1: 15 of the 55 white cells hold `""`).

### Text colour

* the number format's colour tag for the value's section (`[White]`, `[Color2]`, resolved with
  a custom `<indexedColors>` palette; text and logicals use only the TEXT section's tag, a
  numeric section's tag never colours them; errors are shown unformatted - Excel 2026-10-03), else
* the font colour from the core (`styles.font_color`: rgb, theme + tint, indexed; **theme 0 =
  white**, 94 T5; no `<color>` / `auto` = black, as in Excel — LibreOffice paints
  "automatic" text white on dark fills, Excel does not);
* a firing conditional format's font colour replaces the font colour **and beats a number-format
  colour tag** (measured in Excel 2026-10-03: 5 under `[Red]0` with a CF font blue shows blue);
* rich text: every non-blank run is judged with its own colour (a run without a colour uses
  the cell font). A cell fails if any visible run is concealed. A white-font cell whose runs
  are all black is visible.

### Background (its own, never "white" as such)

* no fill → the sheet's white `FFFFFF`;
* solid → fgColor; hatch patterns → the core's fg-over-bg blend;
* **gradient → text is concealed only if it is invisible against every stop and their average**
  (94 toys: the Instructions title is white on a `007B00→020024` gradient, min Lc 81.9 →
  visible; a reader that sees only `patternFill` would call it white-on-white).

### The contrast metric and threshold

APCA-W3 0.0.98G-4g Lc (same formula as `clusters/hidden/final/apca.py`), polarity-aware,
|Lc| from 0 (no contrast) to ~106. APCA's own guidance calls Lc 15 the "point of
invisibility"; the cut is set at **12**, the value with the best agreement with the LLM judge
in the prototype study (report §3 "94": single cuts Lc 10 / 12 / 15 → sol agreement 0.971 /
0.971 / 0.960), so that pale grey text and dark-blue headers with black text pass.

**Hue exemption** (`HUE_EXEMPT = True`, review 2026-10-03; the prototype's v5b
`chroma_exempt`, which the report's chosen design and its toy plan — "00B050 on FF0000 CF fill:
pass", "[Green]/[Cyan] text on white: pass" — rely on). APCA measures lightness only, so
clearly different colours of similar lightness would count as "the same". A low-Lc pair is
still **visible** when all hold: WCAG luminance ratio ≥ 1.1 (`EQUILUM_RATIO`; equiluminant
pairs such as yellow on white stay concealed), CIEDE2000 ≥ 20 (`SAME_COLOUR_DE`), neither colour
dark (CIELAB L* ≥ 40, `CHROMA_MIN_L`; black on navy, blue on navy stay concealed) and at least
one clearly chromatic (C*ab ≥ 40, `CHROMA_MIN_C`).

### Conditional formatting: counts where it fires

The toys contain no CF (none in any 94 toy), so this follows the rubric ("No content should be
concealed by formatting"). Implementation:

1. First pass: each populated cell is judged with its base formatting. Values are read only
   for cells whose style could conceal something (colour-concealed style, a format that can
   blank or colour-conceal some value, or rich text); an untrusted value there makes the cell
   undecided (no fallback; see below).
2. At the end of a sheet, the CF rules that set a font colour, fill or number format
   (main and x14; colour scales by their interpolated colours), plus format-less rules that
   carry `stopIfTrue`, are tested cheaply against every style used on the sheet. Every CF
   outcome some set of firing rules can produce — rules composed in priority order, the first
   firing rule sets each property (font, fill, number format), a firing `stopIfTrue` rule ends;
   conditions and ranges ignored, so a superset of what any one cell sees — is compared with
   the style's own formatting by its **verdict signature**: whether the font colour conceals
   on the background, plus the number format's full profile (the format itself and which of
   its colour tags conceal, unless it can neither blank nor colour any value; on `showZeros=0`
   sheets also whether it lets the option hide a zero). Equal signatures give the same verdict
   for every value (second review 2026-10-04: the earlier test compared a coarse "format is
   risky" flag on single rules and one ordering of rule pairs, and missed e.g. a CF `;;;`
   over `0;-0;;@`, a colour-scale fill under a CF font, and orders lost when two rules share a
   dxf). If no outcome changes any signature, the first-pass result stands (no extra work;
   e.g. red error-check fills under black text, or a PASS/FAIL block whose white text always
   comes with its own green fill). More than 4000 outcomes (`MAX_FLIP_COMBOS`) → second pass.
   Rich-text runs carry their own colours, which this style screen does not see: a sheet with
   rich text and any CF font or fill always gets the second pass.
3. Otherwise the sheet is streamed once more and every populated cell inside those rules'
   ranges is re-judged with its CF evaluated: rules in priority order, the first firing rule
   sets each property, `stopIfTrue` stops — also on a rule with no format (no `dxfId`, the
   classic "Stop If True" blocker) or a format this check ignores (border, bold); colour
   scales apply to numbers only and every interpolated colour (10 samples per segment) is a
   possible fill. A cell whose verdict is the same for every CF outcome is decided without
   reading its value.

Rules evaluated per cell: `cellIs` with literal operands (numbers < text < logicals; text
case-insensitive; `between` takes min/max), `containsText`, `notContainsText` (with `SEARCH()` wildcard
semantics, as Excel evaluates the stored formula: `*` any run, `?` one character, `~` escapes;
measured 2026-10-03: "P*S" and "P?SS" match "PASS"; `checks/_cftext.py`, shared with 66), `beginsWith`, `endsWith` (their formulas use `LEFT`/`RIGHT`: literal),
`containsBlanks`, `notContainsBlanks`, `containsErrors`, `notContainsErrors`,
`expression` when it is a literal, a comparison of **the cell itself** with a literal
(`C4="PASS"`, `0<A1`; relative references are shifted from the first range's top-left cell),
or row/column banding (`MOD(ROW(),2)=0`, `ISODD(COLUMN())`). Other rules (`expression` reading
other cells, `top10`, `aboveAverage`, `duplicateValues`, `uniqueValues`, `timePeriod`) are
**unknown**: both outcomes are tried, and if they disagree the cell is **undecided** (below);
more than 8 unknown rules on one cell make it undecided at once.

**dxf fills** (Excel 2026-10-03, `_fills.py`): a dxf solid fill paints **bgColor only**;
fgColor is ignored; bgColor indexed 64 or `00000000` paints black; no bgColor paints nothing.
So the ChatGPT-tool layout (fgColor X + bgColor indexed 64) paints black, and black text under
such a firing rule is concealed (gpt6 2237).

### Unverified Excel behaviour → no guessing; undecided cells

`_decide` builds every plausible interpretation; when they disagree the cell is **undecided**:
CF font over rich-text runs, number-format colour over rich-text runs, unknown CF rules, and a
zero under a conditional number format on a `showZeros=0` sheet.  (Settled in Excel 2026-10-03
and no longer undecided: booleans go through the text section - `TRUE` under `;;;` is
concealed; a numeric section's colour does not colour text; a CF font beats a number-format
colour; `''` = General and a spaces-only code prints nothing; dxf fills = bgColor only;
containsText wildcards.) A cell is also undecided when its formula value is needed (its formatting
could conceal it) but untrusted (writer policy, missing `<v>`), when it looks concealed inside a
styled Excel table, or when it has dark, directly formatted text (`fontId` ≠ the default xf's)
and no fill of its own inside a `TableStyleDark*` table (table-style fills are not resolved;
Excel's direct formatting is believed to win over the table style's font, so the text may sit
on a dark band — `DARK_TABLE_PROXY` 404040).

**Undecided cells raise `GradingError` only when the verdict depends on them** (review
2026-10-03): if any other cell is certainly concealed the verdict is fail either way, the
certain cells are the mistakes, and `stats.undecided_cells` / `undecided_examples` list the
rest. Otherwise the check raises with the first reason and the count. Undecided cells are kept
as packed integers per sheet, so millions of them stay cheap.

Errors (`#N/A`, `#DIV/0!`) are always shown by the number format (they can still be concealed
by colour).

### Number formats that blank some values

A style's format is "risky" (its cells' values are read) when a section is empty, carries a
colour tag that conceals on the cell's background, or renders blank for one of the probe
values 0, ±1e-9, ±0.4, ±1, "x" **and, for every conditional section `[op t]`, t, t±1,
t±0.5, 2t, 10t, t/2, −t, −10t** (review 2026-10-03: `[>2]"";0` on 5 and `[>=1000]" ";#,##0`
on 5000 were missed by the fixed probes). The verdict itself always comes from rendering the
actual value.

## Edge-case decisions

* **Zeros**: a zero blanked by its format counts (`ZERO_BLANK_COUNTS = True`): the handoff
  rule says "a number format that prints nothing for the cell's value" and the toy Overview
  names `0;-0;;@` on a zero. Check 66 also fails such cells.
* **showZeros=0** (sheet option): a zero the option hides is not counted
  (`SHOW_ZEROS_OFF_COUNTS = False`; `stats.zeros_hidden_by_show_zeros_off`). Measured in Excel
  2026-10-03: the option hides a zero only under General and single-section formats; a format
  with an explicit zero section (three numeric sections) still prints that section, which is
  then judged as usual (`0.00;-0.00;0.00` in white on white fails; `0;-0;;@` prints nothing
  and fails under `ZERO_BLANK_COUNTS`). Two-section formats are read as having no zero section
  (not measured); conditional formats are unmeasured (undecided where it matters). Sheets are
  listed in `stats.show_zeros_off_sheets`.
* **Data bars / icon sets with showValue=0** hide the number behind a graphic: not counted,
  listed in `stats.databar_iconset_value_hidden`.
* **"Stop If True" with no format** (second review 2026-10-04): a rule with `stopIfTrue` and no
  `dxfId`, or a dxf that sets only a border / bold / italics, still stops every lower-priority
  rule when it fires (Excel's documented Stop If True behaviour; check 66 does the same). A
  blocker that cannot be evaluated branches like any unknown rule (undecided where it matters).
  `stopIfTrue` on a data bar / icon set is not modelled (none in the corpus; 0 of 374 files use
  `stopIfTrue` at all).
* Hidden rows / columns / sheets: counted (whole workbook; hiding itself is 92/93's matter).
* Inherited case content (e.g. the Instructions banner) counts like agent content.

## Known limits

* Not modelled: fonts too small to read, values in non-anchor cells of merged ranges, text
  overflowing onto neighbours, column width (`#####`), sheet background pictures, shapes
  covering cells, pivot-table styles (not detected), table styles (not resolved: a cell that
  looks concealed inside a styled table, or dark directly formatted text in a `TableStyleDark*`
  table, is undecided; elsewhere the cell's own formatting is taken as what Excel shows —
  `TableStyleMedium*` header bands are not modelled; the corpus has only Light1 and Medium2 tables).
* Values of formula cells are needed only where the formatting could conceal; files whose
  caches are untrusted (openpyxl-labelled, missing `<v>`) raise there (writer-trust policy
  pending Patrick's ruling).
* CF expressions are evaluated only in the self-reference / banding forms listed above.
