## Rule as implemented

**Fail** when any position of the delivered workbook (every worksheet, dialog and macro sheet,
hidden sheets included, no starting-file diff) is painted **bright yellow** and the workbook's
own text does not explain yellow as an ongoing convention. One mistake per rectangle of
offending cells (per sheet and colour), per row-style run, per column-style run, per sheet
painted by the default style, and per conditional-format rule.

### What counts as bright yellow

`is_bright_yellow(argb)`: HSV hue in **[47.5°, 68°]**, saturation **≥ 0.50**, value **≥ 0.85**
(`HUE_MIN, HUE_MAX, SAT_MIN, VAL_MIN`). Colours are resolved by the core (theme + tint with
Excel's HLS arithmetic, indexed palette including a custom `<indexedColors>`; indexed 13 = FFFF00).

| colour | H / S / V | bright? |
|---|---|---|
| FFFF00 (Excel "Yellow", indexed 13) | 60 / 1.00 / 1.00 | yes |
| FFFF66, FFFF7F | 60 / 0.60, 0.50 | yes |
| FFD700 (gold-yellow), FFCC00 (legacy "Gold") | 50.6, 48.0 / 1.00 | yes (see Questions) |
| FFFF80 | 60 / 0.498 | no (just under) |
| FFFF99 ("light yellow"), FFEB9C (Excel "Neutral"/CF preset), FFEB84 (colour-scale mid) | 60, 47.9, 50 / 0.40, 0.39, 0.48 | no |
| **FFFFCC, FFF2CC** (pale input / answer fills; Patrick: not bright) | 60, 44.7 / 0.20 | no |
| FFFFE0 | 60 / 0.12 | no |
| FFC000 (Excel "Orange", Office accent 4 "Gold") | 45.2 / 1.00 | no (hue) |
| CCCC00, 808000 (dark yellow / olive) | 60 / 1.00 / 0.80, 0.50 | no (value) |
| F5E6C0, FEF3E2 (beige bands in 47 T1) | 43, 36 | no |

What a fill paints: solid → fgColor (core); hatch patterns → the core's fg-over-bg blend;
**gradients → bright if any stop is bright** (it is painted somewhere in the cell).

**Unresolvable fill colours (47-R2-08, 2026-10-04).** A fill colour the core cannot resolve (an rgb
that is not 6 or 8 hex digits such as `FFGGFF00`, a theme index outside the 12 slots, an indexed
value outside the palette other than 64 / 65, an invalid custom `<indexedColors>` entry, a tint
that is not a number in [-1, 1]) is an explicit `UnknownColour` (core `styles.resolve`), never "no
fill". The first time a position the check examines - a cell, a row / column style, style 0, a
conditional format's painted colour - uses one, the check splits into one **reading** per way
Excel could paint it: **no fill**, **bright yellow FFFF00**, **another (not bright) colour**; with
several distinct unknown colours, every combination (at most `MAX_UNKNOWN_FILL_COLOURS` = 4,
3^4 = 81 readings; a fifth distinct one raises). Each reading is a full copy of the check, so the
swatch, legend and WIP logic is applied to every reading exactly as to known colours. **All
readings agree → that verdict** (the reading with every unknown colour as no fill; stats
`unresolved_fill_colours` (colour, why, first use) and `unresolved_fill_readings`, and the summary
says the readings agree); **they disagree → `GradingError`** naming the colours, where each was
first used, and one reading that passes and one that fails. A colour no examined position uses
(a style no cell uses, a solid fill's bgColor, a dxf's ignored fgColor, a font colour) never
matters; workbooks without one run a single reading at no extra cost. Equal stored references
are one unknown (Excel renders one stored value one way); "another colour" is one dark colour per
unknown, so it never equals a known neighbour's fill (the header-band test of key samples).

### Sources of paint

| source | where it applies | location in the mistake |
|---|---|---|
| a cell's own fill | every `<c>` element: constants, formulas, spill/array members (no formula of their own), empty styled cells | rectangles, e.g. `'Daily Model'!AIH94` |
| row style (`<row s=.. customFormat="1">`) | the row's positions without a `<c>` | `'S'!5:6` (consecutive rows of one colour grouped) |
| column style (`<col style=..>`) | positions without a `<c>` or row style; overlapping `<col>` entries are read the shared way (`SheetHead.col_segments`): the later entry - by `min`, then file order - wins on the columns it covers, so an overridden style paints nothing there (2026-10-04) | `'S'!C:D` |
| default style 0 | every empty position of every sheet | bare sheet name |
| conditional format (main and x14 rules with a dxf fill) | the rule's sqref, **counted always** — whether or not it can fire today (`CF_COUNTS_ALWAYS`) | `'S'!B2:B9,D2` |

Never counted: font colour, sheet tab colour, colour scales (a heat map, even with a yellow
mid-point), data bars, icon sets, table-style and pivot-style formatting (not resolved), shapes.

**Conditional formats: decided by the rubric, not the toys** (no toy has a yellow CF rule).
The rubric names "conditional formatting on error-check rows" as a yellow *usage* that must be
explained in the glossary; the rule itself is the usage, so it counts whether or not it fires.
This also avoids evaluating CF conditions.

**Conditional-format (dxf) fills** (`_fills.dxf_fill_paints`, core `styles.fill_paint(..., dxf=True)`):
Excel paints **bgColor only** (measured by Patrick 2026-10-03, `out/excel_session_answers.md`
Q2). fgColor is ignored; bgColor indexed 64 and bgColor rgb `00000000` paint **black** (alpha
ignored); no bgColor means no fill. So Excel's own layouts (bgColor alone; Excel Online's
`fgColor indexed="64"` + the colour in bgColor) paint the bgColor colour; ChatGPT's tool
(`fgColor` = colour + `bgColor indexed="64"`) and openpyxl's `PatternFill(start_color=X,
fill_type="solid")` (`bgColor rgb="00000000"`) paint black, never yellow; a dxf with fgColor
only paints nothing. There is no ambiguity left: the former `stats.cf_ambiguous` and its
"cannot decide" `GradingError` are removed. (An `auto="1"` bgColor is read as black like
indexed 64; not measured on its own and absent from the corpus.)

**A conditional-format fill whose colour cannot be resolved** (an UnknownColour: a theme / indexed
index beyond the palette, an invalid rgb ...) is **not counted** (Patrick 2026-10-05: "CONDITIONAL
FORMATS never stop a grading" - the rule is taken as off for this check). Until 2026-10-05 it was a
reading of the unresolvable-colour fork (no fill / bright yellow / another colour) and could raise
"the verdict depends on unresolvable fill colour(s)". Each such rule is listed in
`stats.cf_assumptions` (`rules`, `examples`). An unresolvable colour of a cell, row, column or default
style is still graded under every reading as before.

### The legend exception

Text sources (whole workbook, any sheet, hidden included): constant text cells (shared and
inline strings; **not** formula results), cell comments (legacy notes and threaded comments),
and drawing text boxes / shapes (`txBody` paragraphs). Header/footer text is not read.

A text **mentions yellow** when it contains `yellow` (also `yellows`, `yellowish`,
`bright yellow`, `yellow-highlighted`) or the hex `FFFF00` (also its ARGB spelling `FFFFFF00`),
**not** preceded by a pale qualifier (`light`, `pale`, `soft`, `pastel`, `faint`, `muted`,
`cream(y)`): "Light yellow = inputs" explains pale fills, not bright yellow.

Each clause that mentions yellow (split on newlines, `;`, bullets and sentence ends) is
classified, in this order. A clause that follows one of them and opens with a pronoun ("Yellow
is not used for inputs; **it** marks the output cells") is read with "yellow" in the pronoun's
place, so the second clause is classified too (2026-10-04).

Categories of cells (`_CAT`): *inputs, assumptions, outputs, drivers, (error) checks, hard-coded,
formulas, links, results, answers, constants, scenarios, switches, parameters, estimates,
forecasts, actuals, historicals, overrides, sources, key <x>*.

A text's class is its most permissive clause (DEFINES > WIP > TEMPLATE > NEGATED > MENTION).

**TEMPLATE lines do not excuse** (review 2026-10-03): almost every GPT-6 file explains the
case's pale answer fill ("Questions retains … yellow answer fill"); every case's own yellow is
pale (FFFFCC inputs, FFF2CC answers: report §3 "47"), so such a line explains no bright yellow,
and counting it as a legend would excuse any bright-yellow WIP cell elsewhere in the file. It
does not block other legend lines either. A short
colour label cell ("Yellow", "Yellow fill:", **"Yellow (FFFF00)", "Yellow Fill (#FFFF00)"** —
a trailing colour code is allowed) is joined with the next one or two text cells to its right
on the same row (within 3 columns) before classifying: `Yellow | Key outputs` → "Yellow = Key
outputs". If nothing is to its right, the nearest text to its left is used ("Inputs | Yellow"
→ "Inputs = Yellow"; a definition only when the left text names cells, see the DEFINES row:
"Cost schedule | Yellow" in a RAG status column is a MENTION). If texts sit on both sides, the left one is also classified as
"<left> = <colour>", but that extra line is kept **only when it is WIP or NEGATED** (it can
restrict, never excuse): attempt 2226 `Cover!A29:C29` "Review / Unfinished | Yellow Fill
(#FFFF00) | None remaining in final deliverable" gives a NEGATED and a WIP line.

**Excuse**: any DEFINES line anywhere excuses all bright yellow in the workbook (handoff rule;
no coverage test — see Questions), **unless** some text in the workbook defines yellow as
unfinished (a WIP line; `WIP_LEGEND_BLOCKS_EXCUSE = True`): the workbook's own key then says
its yellow may be leftover work, so another line cannot make it an explained convention
(rubric "bad": yellow "indistinguishable from leftover WIP markers"). NEGATED lines do not block.
**Never excused**: bright-yellow cells whose own text, or comment, is a placeholder marker
(`WIP_CONTENT_OVERRIDES_LEGEND`): TBD, TBC, TBA, to do, placeholder, WIP, fix me, to be
confirmed / determined / completed / updated / provided / added, update later, confirm with,
check this, to confirm, not yet confirmed / final / known / available, still to, fill in
later, dummy, `???`, `xxx`. Those stay mistakes (rubric "bad": yellow flagging TBD items).
Without a legend they are named inside the block's mistake ("G11 says 'TBD'").

### Legend swatches (sample cells)

A swatch is documentation, not highlighting, and is never a mistake. Conditions (all):
no bright-yellow cell directly left or right of it (a sample **merged across 2–3 empty cells**,
a `mergeCell` range of one row, counts as one sample; the same cells unmerged are a band,
2026-10-04), and one of:

1. **Empty sample + label that starts with the colour word**: the first non-empty cell 1–2
   columns to the right is a text starting with "yellow" ("Yellow fill = key output cells"),
   or a text starting with "yellow" sits within 3 columns to the left (`Yellow | Unfinished -
   none in this file | [sample]`, attempt 4060 layout; `Yellow fill | [sample] | Unfinished /
   review (none in delivered file)`, the 3439 layout with the sample in the middle — the
   colour-word label wins over the plain text on the other side, 2026-10-04). The label line,
   classified as above, decides whether the rest of the yellow is excused; the sample itself is
   documentation even when that line is WIP or NEGATED (a legend row that says "Yellow fill =
   TBD" with no yellow cell elsewhere passes).
2. **Self-labelled sample with the colour word**: a bright-yellow text cell whose own text
   starts with the colour word and is a bare colour label ("Yellow fill" next to its meaning,
   corpus 3439 `Cover!A19`) or a DEFINES / NEGATED line ("Yellow fill = Unfinished / review
   (none in delivered file)"). A yellow **note** that defines nothing or marks unfinished work
   ("Yellow flag: discount rate TBD - confirm with client") is highlighting, not a sample.
3. **Label without the colour word** — common colour keys, written as
   `[sample] | Key output cells` (right label), `Key outputs | [sample]` (left label, 1–2
   columns) or `[yellow "Key output"]` (the sample holds its own meaning). Required for all:
   the label is not WIP / negated (`classify_label`); the cell before the line holds no value /
   formula / text (a legend header text is allowed); no number or formula in the 3 columns after
   the label (`KEY_LINE_CLEAR_COLS`; for a left label nothing at all may follow the sample, for
   a self-labelled sample a description text may follow). Then:
   - **right label**: (a) a **legend header** (*legend, colour key / code / coding /
     conventions / scheme / guide, formatting key / conventions / guide, conventions, key to
     colours, glossary, cell key / styles / formatting*, ≤ 60 chars) up to 15 rows above within
     3 columns; or (b) a **colour key block**: another colour's sample within 3 rows in the same
     column (an empty filled non-yellow cell with a text label beside it whose fill differs, or
     a filled non-yellow text cell) **whose label names a cell category** (`is_key_label`) — a
     red/amber/green status column of section names is not one; or (c) the label itself names a
     cell category (≤ 60 chars: *inputs, assumptions, outputs, formulas, calculations, links,
     checks, hard-coded, drivers, historicals, actuals, sources, constants, answers, key
     figures/metrics/values/cells*; not *totals / results*, which are ordinary row labels) and
     the cell right of it is empty, **and the label does not head a table**: no label / value
     row (a text in the label's column ± 1 with a number or formula within 3 columns to its
     right) in the 2 rows below it (`TABLE_ROWS_BELOW`; "[yellow] | Inputs" over "Growth |
     5%" is a section header with a marker, 2026-10-04);
   - **left label / self-labelled**: the label must name a cell category (`is_key_label`),
     plus a legend header or a key block; a left label also qualifies alone (c, same
     table-header guard).
   Such a label counts as a DEFINES legend line.

Every other bright-yellow cell is an ordinary offender (e.g. `Discount rate | [yellow] |
TBD`, `[yellow] | Discount rate - TBD` under a "Conventions" header, `Discount rate | [yellow]`
under a "Legend" header, `[yellow] | Working notes` with no legend context, `[yellow] |
Revenue assumptions | | 0.05` (numbers after the label), `[yellow] | Total costs`, two
adjacent yellow cells).

The row of a swatch may hold data further right: in 47 T3 the legend `A4:B4` shares row 4
with the row label `F4` and the time series `H4:DW4` (outside the 3-column window).

## Edge-case decisions

* Whole workbook: inherited case fills count like agent fills (handoff). Pale case fills are
  out of the band anyway; a case that ships bright yellow fails unless explained.
* Hidden sheets, hidden rows/columns: counted.
* Formula-result text is not read as legend text (it would need values; legends are typed).
* A positive legend anywhere excuses every bright-yellow source, including CF rules and
  row/column styles, but not WIP-content cells; not when some text defines yellow as
  unfinished (`WIP_LEGEND_BLOCKS_EXCUSE`); TEMPLATE lines excuse nothing.
* A WIP comment on a bright cell (comment text matches the placeholder markers) is a WIP cell.
* Mistakes: per sheet, per colour, rectangles of own-fill cells (`_rects`, same algorithm as
  `refs.group_cells`, built from horizontal runs so memory stays small); capped at 25 by the base.
* **Unreadable text** (a shared-string index out of range, 2026-10-04): the cell is treated as
  opaque data while streaming; at the end the check raises `GradingError` only when the workbook
  has any bright-yellow source (the unreadable text could be the legend that excuses it, or the
  WIP line that blocks the excuse). Without yellow the verdict cannot depend on it: pass.

## Known limits

* Table styles, pivot styles, sparkline/chart colours, shapes' fills, cell pictures: not read.
* Text in charts, headers/footers, data-validation input messages: not read as legend text.
* The legend matcher is English-only and regex-based; unusual phrasings fall to MENTION
  (no excuse) — conservative by design. Clauses are split on sentence ends, so a back-reference
  ("its yellow fill is explained above", GPT-6 2356) is read without its antecedent.
* A swatch label is judged from its own row only (3-column windows); legend tables laid out
  differently (label two rows away, merged label cells, a sample merged over more than 3 cells
  or over several rows) fall back to ordinary offenders.
* Dark or desaturated yellows outside the band (e.g. D4C200) are not "bright".
* A legend written in the colour's own name for a gold hue inside the band ("Gold fill = key
  outputs" with FFD700, "Amber = …" with FFCC00) is not recognised: `mentions_yellow` knows
  *yellow* and FFFF00 only (Question 14; no corpus file uses these hues).
* An unresolvable fill colour is graded under every reading (no fill / bright yellow / another
  colour; see "What counts as bright yellow"); more than 4 distinct ones on examined positions
  raise. "Another colour" never equals a known colour, so a reading in which the unknown happens
  to equal a neighbour's fill is not tried. No corpus file has one (2026-10-04 scan,
  `scratch/core_fixes/scan_core.py`: the only unresolvable references are `indexed="81"` font
  colours of comment fonts no cell uses).
