# `data/` — the benchmark tasks

The 101 tasks a run or a grading needs, so that a reviewer with no access to
our database or object store can reproduce the experiments. The task rows are
checked into the repository; the task workbooks (starting files and golden
solutions) are downloaded separately and placed here by
`scripts/install_task_files.py` (README, "Task files"). Nothing under `data/`
is regenerated by the pipelines; it is produced once by
`scripts/export_benchmark_data.py` (which needs read-only credentials in
`config/config.yaml`) and verified by `scripts/verify_offline_bundle.py`
(which needs nothing).

All paths written into any JSON here are **repo-relative, POSIX-separated**
(`data/tasks/task_id=1/starting_files/ApfelInc.xlsx`). Loaders join them onto
the repository root. When `local.data_root` in `config/config.yaml` is not the
default `data`, loaders replace the leading `data/` with that root.

```text
data/
  MANIFEST.json                     every task file: path, original object-store key, size, sha256
                                    (what the installer and the verifier check against)
  tasks/
    tasks.json                      the 101 rows of the `tasks` table (list, same objects as below)
    task_id=<N>/
      task.json                     one `tasks` row, all columns; the two file columns rewritten to
                                    repo-relative paths, the original keys kept under "s3_keys"
      starting_files/<name>         byte-for-byte copies (workbook, case PDF, context documents)
      solution_files/<name>         byte-for-byte golden solution(s)
                                    Both NOT tracked in git: installed from the downloaded zip by
                                    scripts/install_task_files.py, sha256 checked against MANIFEST.json
```

Rows are the database rows, verbatim: every column under its column name,
timestamps as ISO-8601 strings with an offset, JSON/JSONB columns as nested
JSON, the file columns rewritten to repo-relative paths with the original
object-store keys preserved under `"s3_keys"` (the bucket name reduced to
`<bucket>`).

Workbook file properties (creator, last-modified-by) are set to a neutral value
by `scripts/scrub_workbook_metadata.py`; cells and formulas are untouched.

## `outputs/` — what an offline run writes

Runs and gradings never write into `data/`. They write under `outputs/`
(`local.output_root`, gitignored):

```text
outputs/
  <agent_model_name>/                 the cohort label verbatim (a label such as
                                      openpyxl_anthropic/claude-fable-5-1-max nests one level)
    task_attempts.jsonl               one task_attempts-shaped row per attempt, same fields as
                                      the database row; attempt_files / prompt_files are
                                      repo-relative paths under the folder below
    task_id=<N>/<YYYYmmdd_HHMMSS>/    exactly the artifact set the cloud sink uploaded for that
                                      pipeline: the solution workbook first (the judged file),
                                      then the prompt files as sent, transcript, request log,
                                      metadata (the starting workbook is not copied; it is in data/)
  gradings/
    gradings.jsonl                    one gradings-shaped row per grading, same fields as the
                                      database row; raw_files_path points at the folder below
    <grading_id>/                     the judge's staged files (what raw_files lists)
```

Local ids: a row's `id` is the millisecond epoch time at which it was written
(an integer, unique across concurrent lanes on one machine). `attempt_id` in a
local grading is the `id` of the attempt row it graded.

Skip-if-attempted / resume logic reads the same `task_attempts.jsonl` files it
appends to.

## Size

The task rows are a few hundred kilobytes. The 202 task workbooks (about
430 MB, 383 MB zipped, two goldens above 60 MB) are not tracked: they are
downloaded once and installed by `scripts/install_task_files.py`, which checks
them against the hashes in `MANIFEST.json`.
